- 2026-10-15 — Bug report (owner, 2026-10-14: iPhone ⇄ old Android 1:1 went choppy → frozen → robotic audio; WhatsApp fine). Fix on fix/home-broadband-call-quality (ADR-0010, Proposed). **Root cause (lab-reproduced): CPU overload on the weak peer, not the network.** 1:1 used software AV1 at 720p30, which costs ~8× VP8/H264 per frame (33 vs 4 ms at 1 core). Chrome never reports `cpu` limitation for it, and nothing stepped down. On a starved peer the remote hears 18–63 % of its audio concealed. Fixes: constrained devices (phones, ≤ 2 cores, ≤ 4 GB) never negotiate software AV1/VP9. A CPU overload guard (1 Hz): reduced (VP8/H264, ≤ 360p15 both ways), then paused (audio only, calm notice), with headroom-gated recovery. Interleaved A/B (720p camera, one peer docker-limited): remote's audio concealment 27.0 → 3.3 % (1 core), 56.3 → 9.1 % (0.5 core), freezes about halved, VMAF −6 to −9 (deliberate 360p15). The home Wi-Fi hypothesis did not reproduce: new profiles home_wifi / home_wifi_busy look fine on the staging behaviour. good_wifi / 3g_lossy within noise. Lab additions: `--cpus p1=<cores>`, `--hd`, profile `jitter_distribution` / `queue_ms`, metrics recv_fps_min / decode_ms / cpu_limited_ratio. E2E: `cpu-guard.spec.ts`, and `E2E_DOCKER=1` runs Chromium in the lab image (local browsers can't launch in some agent sessions).

# Architecture

Status legend: **Decided** = build on it. **Proposed** = default we'll use unless the owner objects. **Open** = needs an owner decision.

## 0. The constraints fight each other — here is how we resolve it

| Requirement | Tension | Resolution |
|---|---|---|
| Peer-to-peer, no server | 10-person **video** mesh means every phone encodes and uploads 9 streams. At 400 kbps each = 3.6 Mbps up + 9 encoders: phones overheat, cellular uplinks collapse. Violates "minimal bandwidth" and "anyone with stable internet". | **Hybrid topology** (ADR-0002): true P2P for 1:1 and ≤3 participants; a managed serverless SFU (Cloudflare Realtime) for 4–10. Each phone then uploads *one* simulcast stream regardless of call size. |
| No server | Calls can't ring a phone whose app is closed without a push. APNs requires a signed request from something holding our key. | One Cloudflare Worker (free tier) does signaling + push relay. This is the "lambda" the constraints allow. |
| Anyone can connect | ~10–20% of mobile users sit behind symmetric NAT/CGNAT where P2P fails without a relay. | Cloudflare Realtime TURN. Shares the SFU's free 1,000 GB/month egress. |
| No background noise | ...but music must survive. Noise suppressors are trained to delete music. | Two explicit modes: **Voice** (ML noise suppression + AEC + AGC) and **Music** (NS/AGC off, Opus fullband stereo, higher bitrate). Auto-detect is a later stretch goal. |
| Minimal bandwidth | ...but superior quality | Modern codecs (Opus w/ FEC+DTX+RED; AV1/VP9 where hardware allows, H.264 fallback), receiver-driven layer selection, and bandwidth budgets enforced as test gates. |

## 1. Platform & build — Decided
- **iOS:** Swift 6, SwiftUI, iOS 17+ minimum (Proposed). Project generated by **XcodeGen** from `ios/project.yml` — `.pbxproj` files are unmergeable and hostile to agents, so they are build output.
- **Android:** Kotlin 2.x, Jetpack Compose, minSdk 26 / targetSdk latest (Proposed). Gradle Kotlin DSL + `libs.versions.toml`. JDK 21 toolchain.
- **No cross-platform UI framework.** The UI is tiny; the hard parts (audio session, CallKit/Telecom, camera, codecs, push) are platform-specific anyway. A cross-platform layer would add a bridge between us and the media stack, which is where quality is won.
- **Shared logic is shared by contract, not by code:** `protocol/` JSON Schema + fixtures, and shared Maestro E2E flows. Revisit Kotlin Multiplatform for the call state machine only if the two implementations start drifting (ADR if so).

## 2. Media stack — Proposed
- **libwebrtc** on both platforms via the maintained prebuilt `webrtc-sdk` builds (iOS SPM `WebRTC`, Android `io.github.webrtc-sdk:android`). Same engine as Chrome → the quality bots measure the same code paths.
- **Audio:** Opus 48 kHz. Voice mode: 24–32 kbps mono, in-band FEC, DTX, RED (redundant encoding) on lossy links; WebRTC AEC3 + platform voice processing; ML noise suppression (candidates: RNNoise — tiny, CPU-cheap; DeepFilterNet — better, heavier. Pick by DNSMOS score vs battery in the quality lab). Music mode: 64–128 kbps stereo, `maxaveragebitrate`/`stereo=1`, NS/AGC/HPF off, AEC kept on unless headphones.
- **Video:** codec negotiated per device capability. Order of preference to evaluate in the lab: AV1 (best bits-per-quality, Meet uses it on mobile at low rates; HW encode is rare, SW encode at ≤360p is feasible) → VP9 SVC → H.264 hardware (universal fallback, lowest battery). The lab decides, not opinion.
- **Group (SFU) path:** simulcast 3 layers (e.g. 180p/360p/720p) or SVC; receiver subscribes to the layer it actually renders (active speaker big, others thumbnail). Audio: subscribe to top-3 loudest only via audio-level header.
- **E2EE:** P2P is already end-to-end (DTLS-SRTP). On the SFU path add frame encryption (SFrame-style via libwebrtc `FrameEncryptor/Decryptor`) with keys exchanged over the signaling channel encrypted to each member's device key. The SFU then only sees ciphertext.

## 3. Topology — Proposed (ADR-0002)
- 2–3 participants: full mesh P2P, ICE with STUN + Cloudflare TURN fallback.
- 4–10 participants: everyone publishes to Cloudflare Realtime SFU. Upgrade/downgrade mid-call is a renegotiation, not a new call.
- Free-tier math: 10-person video ≈ 10 × ~1.5 Mbps downstream ≈ 6.75 GB/hour of SFU egress → ~145 ten-person call-hours/month free. 1:1 P2P calls cost nothing; TURN-relayed 1:1 ≈ 0.5–1 GB/hour.

## 4. Serverless edge — Proposed
One Cloudflare Worker, Durable Objects (SQLite-backed, free plan):
- `UserDO` per user: WebSocket (hibernation API) for presence + signaling mailbox, registered push tokens.
- `CallDO` per call: membership, roster, topology switch, E2EE key epoch.
- Push relay: APNs **VoIP push** (PushKit, required to ring via CallKit) and FCM high-priority data messages.
- Mints short-lived TURN credentials and SFU session tokens (the app secret never ships in the app).
- Stores nothing about call content. Retains only: public key, contact-discovery hashes, push tokens.
Why not AWS Lambda: signaling wants long-lived WebSockets; API Gateway WebSocket free tier expires after 12 months and Lambda has no equivalent of a stateful Durable Object for a call room.

## 5. Calling UX integration — Decided
- iOS: **CallKit** + PushKit (Apple *requires* reporting a CallKit call for every VoIP push or the app gets killed). `AVAudioSession` `.playAndRecord` / `.voiceChat` (Voice mode) / `.default` with voice processing toggled (Music mode).
- Android: self-managed **ConnectionService / Core-Telecom (`androidx.core:core-telecom`)**, foreground service of type `phoneCall|camera|microphone`, full-screen intent notification for ringing.

## 6. Identity, onboarding, contacts — Open (needs owner decision)
Each install generates a device keypair (Secure Enclave / Android Keystore). Identity = public key. The question is how people *find* each other:
- **A. Phone number + SMS OTP** (WhatsApp-like, contacts "just appear"). Needs a paid SMS provider or Firebase Phone Auth (billed). Small but non-zero cost; best UX.
- **B. Invite link / QR** (free, unspoofable, private). User taps "Invite" → share link via WhatsApp/SMS → friend installs → you're connected. Address-book contacts show an "Invite" button until they join.
- **C. Sign in with Apple / Google + hashed-phone discovery.** Free, one tap, but unverified phone claims can be spoofed.
Recommendation: ship **B** for v1 (zero cost, zero spoofing), design the identity layer so **A** can be added later.

## 7. Quality lab — Decided (see `quality/CLAUDE.md`)
- Headless **bot peers**: a minimal web client in `quality/webpeer` speaking our protocol, driven by Playwright in Chrome with `--use-file-for-fake-{video,audio}-capture`. Lets one laptop simulate a 10-person call.
- **Network impairment:** Linux `tc netem` in Docker for bots; Android emulator network shaping; Network Link Conditioner / a netem gateway for physical devices.
- **Scorers:** VMAF + PSNR/SSIM (video, frame-aligned via embedded frame-ID codes), ViSQOL (audio full-reference), DNSMOS P.835 (noise suppression, no reference), mouth-to-ear & glass-to-glass latency via coded chirps/timestamps, WebRTC `getStats` (bitrate, freezes, concealment, jitter-buffer delay, quality-limitation reason).
- **Gates:** `quality/thresholds.yaml` per network profile, including **max bitrate** (the bandwidth budget). Owner-controlled; agents may not edit it.
- **Remote:** staging Worker + bots in GitHub Actions + real devices on Firebase Test Lab / own devices over real networks, same scorers.

## 8. Testability requirements on the apps
- `qa` build configuration/flavor with: file-backed audio/video capturers, received-media recorders, `getStats` exporter (JSON lines), deep links `betterapp://qa/...` to join a room without UI.
- Every screen reachable by deep link for screenshots and Maestro.
